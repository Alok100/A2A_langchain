# Agent Architecture — Node Context Reference

This document explains the **context and role of each node/box** in the manager’s structure diagram: **AGENTS -2026-02-06-1829.png**.

---

## 1. User interaction & entry

| Node | Context | What it does |
|------|--------|----------------|
| **UserChat / Voice / App** | Primary user interface. | Entry point for all requests: text chat, voice, or in-app. Sends raw user input into the pipeline. |
| **NLP & Intent Detection** | First processing step. | Uses NLP to infer **intent** (e.g. “check leave balance”, “submit timesheet”) and extract **entities** (dates, IDs, names) from free-form input. |

---

## 2. Orchestration & authorization

| Node | Context | What it does |
|------|--------|----------------|
| **LangGraph Orchestrator** | Core flow and state manager. | Runs the end-to-end flow: coordinates agents, tools, and decision points so the system responds in a coherent, stateful way. |
| **Role Validator Employee / Manager / HR** | Security and authorization gate. | Authenticates the user and resolves their role (Employee, Manager, HR). Used to enforce permissions and limit actions by role. |
| **Agent Router A2A Dispatcher** | Central router to specialized agents. | After role validation and intent detection, routes the request to the right **specialized agent** (Attendance, Leave, Timesheet, Asset). “A2A” = Agent-to-Agent dispatch. |

---

## 3. Specialized agents & data (domain layer)

| Node | Context | What it does |
|------|--------|----------------|
| **Attendance Agent** | Domain agent for attendance. | Handles attendance-related requests: view records, request adjustments, answer attendance policy questions. Talks to **Attendance MCP Server** for data. |
| **Attendance MCP Server** | Service layer for attendance. | Bridges **Attendance Agent** and **Attendance Database**: implements the protocol/API used to read and write attendance data. |
| **Attendance Database** | Persistent attendance store. | Stores attendance records: clock-in/out, leave applications, adjustments, history. |
| **Leave Management Agent** | Domain agent for leave. | Handles full leave lifecycle: apply, check balance, policy checks, approvals, status. Often calls **Policy Query Agent** and can drive updates in attendance-related data. |
| **Timesheet Agent** | Domain agent for timesheets. | Handles timesheet submit/approve and queries (hours, projects). Uses **Timesheet MCP Server** for data. |
| **Timesheet MCP Server** | Service layer for timesheets. | Bridges **Timesheet Agent** and **Timesheet Database** for timesheet reads/writes. |
| **Timesheet Database** | Persistent timesheet store. | Stores timesheets: hours, project allocation, approval state. |
| **Asset Agent** | Domain agent for assets. | Handles asset requests: assign, report lost/damaged, availability, inventory. Uses **Asset MCP Server** for data. |
| **Asset MCP Server** | Service layer for assets. | Bridges **Asset Agent** and **Asset Database** for asset reads/writes. |
| **Asset Database** | Persistent asset store. | Stores assets: type, serial, allocation, maintenance, status. |

---

## 4. Policy & decision

| Node | Context | What it does |
|------|--------|----------------|
| **Policy Query Agent** | Policy retrieval and interpretation. | Given context or a request, queries the **Policy PDF Vector Database** to return relevant policy text/clauses. Used by other agents and the **Decision Engine** for compliance. |
| **Policy PDF Vector Database** | Policy knowledge base. | Holds vectorized (embedded) policy content (e.g. from PDFs). Enables semantic search so the **Policy Query Agent** can find policies by meaning, not just keywords. |
| **Decision Engine** | Central decision maker. | Combines user request, data from domain DBs, and policy from **Policy Query Agent** to decide: **Auto Approve** or **Policy Violation**. |
| **Auto Approve** | Outcome: compliant request. | Path when the request fully meets policy and rules; no human needed. Flow continues to **Execute Action DB Update**. |
| **Policy Violation** | Outcome: non-compliant request. | Path when the request conflicts with policy. Flow goes to **Human Escalation HR / Manager**. |

---

## 5. Execution, escalation & reporting

| Node | Context | What it does |
|------|--------|----------------|
| **Performance & Efficiency Agent** | Monitoring and analysis. | Sits after decision outcomes; can track auto-approvals, violations, agent performance, and efficiency. May log events or feed metrics before actions/escalations complete. |
| **Human Escalation HR / Manager** | Human-in-the-loop. | Receives **Policy Violation** (and optionally complex cases). Sends to HR or managers for review and manual decision. |
| **Execute Action DB Update** | Write path for approved actions. | Performs the actual DB writes: e.g. approve leave in **Attendance Database**, update **Timesheet Database**, update **Asset Database**. |
| **Notification Agent** | Outbound messaging. | Sends alerts and status updates (approved, rejected, reminders) to users, managers, or HR. |
| **Slack / Email / App** | Notification channels. | Delivery channels used by **Notification Agent**: Slack, email, in-app. |
| **Monthly Reports Managers & HR** | Periodic reporting. | Produces periodic (e.g. monthly) reports for managers and HR from agents/DBs: attendance, leave, timesheets, assets, compliance. |
| **Audit Logs** | Accountability and compliance. | Records all important events: user actions, agent decisions, policy checks, escalations, DB updates. Used for auditing, security, and incident review. |

---

## End-to-end flow example

1. **UserChat / Voice / App** — User asks (e.g. via chat): “What’s my leave balance?”
2. **NLP & Intent Detection** — Intent: “leave balance inquiry”; entities as needed.
3. **LangGraph Orchestrator** — Drives the flow.
4. **Role Validator** — Confirms user role (e.g. Employee).
5. **Agent Router A2A Dispatcher** — Routes to **Leave Management Agent**.
6. **Leave Management Agent** — Uses **Attendance MCP Server** and **Attendance Database** for leave history; for “apply leave” would also call **Policy Query Agent** and **Policy PDF Vector Database**.
7. **Decision Engine** — Decides **Auto Approve** or **Policy Violation**.
8. If **Auto Approve** → **Execute Action DB Update** (if any) → **Notification Agent** → **Slack / Email / App**.
9. If **Policy Violation** → **Human Escalation HR / Manager**.
10. **Audit Logs** record the whole path.
